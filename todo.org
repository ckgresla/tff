* ChoosyTransformer
Core idea: a pool of N transformer layers, where a router dynamically selects which layer to apply at each of K computational steps. Unlike a standard transformer (fixed order) or a looped transformer (same layer repeated), the model learns to compose different layers for different inputs.

** Architecture
- Pool of N distinct transformer blocks (each with unique weights)
- Router MLP: mean-pools hidden state → logits over N layers
- K routing steps per forward pass (N and K are independent hyperparameters)
- At each step: router picks a layer, that layer is applied
- Training: categorical sampling from router logits (exploration)
- Inference: argmax routing (exploitation)

** Adaptive Computation (future work)
The model should learn /how many/ steps to take, not just which layer at each step.

*** Per-batch halting probability
- Core idea: use per-token loss as a signal for computational difficulty
- Tokens with high loss (model is uncertain) → allocate more routing steps
- Tokens with low loss (model already understands) → fewer steps (as low as 1)
- This creates a natural curriculum: easy tokens get fast-tracked, hard tokens get more compute
- Implementation sketch:
  1. Router outputs both "which layer" and "should I halt" at each step
  2. Halting probability trained to correlate with loss reduction per step
  3. If adding another step doesn't reduce loss much → halt

*** Max computational steps (critical)
- MUST enforce a maximum number of steps to avoid the halting problem
- Without a cap, the model could learn to loop forever on hard tokens
- A hard cap (e.g., K_max = 2 * num_pool_layers) is the simplest approach
- But a SOFT cap is more elegant and learnable:
  - Add a "ponder cost" to the loss: lambda * mean(num_steps_taken)
  - This is analogous to a repetition penalty in LLM decoding
  - The model learns to balance "more compute = lower CE loss" against "more compute = higher ponder cost"
  - With the right lambda, the model naturally converges to using just enough steps
  - See: Graves (2016) "Adaptive Computation Time" (ACT) for the original formulation
  - The ACT halting mechanism uses:
    - Per-position halting probability p_t = sigmoid(W * h_t + b)
    - Cumulative probability sum tracked per position
    - Position halts when cumulative prob exceeds 1 - epsilon
    - Remainder probability used to weight final state
    - Ponder cost = act_loss_weight * mean(num_updates + remainders)
  - Bias initialization matters: bias_init=1.0 encourages continuing (not halting too early)

*** Soft max steps vs hard max steps
- Hard max: simple, guarantees bounded compute, but model can't learn the bound
- Soft max (ponder cost): model learns optimal compute allocation, but needs tuning of lambda
  - Too high lambda → model always halts after 1 step (degenerate)
  - Too low lambda → model uses max steps always (no adaptivity)
  - Sweet spot: model uses varying steps depending on input difficulty
- Recommended approach: use BOTH
  - Hard max as a safety net (K_max)
  - Ponder cost for the model to learn within that budget
  - Start with hard max only (simpler), add ponder cost as refinement

** Router Loss Terms
*** Load balancing (KL to uniform)
- Without this, routers /may/ collapse to using 1-2 layers and ignoring the rest
- Loss: KL(empirical_layer_usage || uniform) or simpler MSE variant
- Weight: start with 0.01, ablate to see if collapse happens without it
- IMPORTANT: we want to ablate this explicitly to see if layer collapse occurs
  - Run with and without balancing loss
  - Measure layer utilization entropy (should be high with balancing, may be low without)
  - If the model naturally uses all layers without the loss, that's interesting!

** TODO ablate router training strategies
- Current: Gumbel-softmax with straight-through estimator (hard forward, soft backward)
- Alternative approaches to compare:
  1. Gated routing (Switch Transformer style): scale output by router probability
     - Concern: dilution when router is uncertain (early training, gate ≈ 1/N)
  2. Soft routing: apply ALL layers, softmax-weighted combination during training
     - Full gradients, but N× compute per routing step
     - Hard routing at inference only
  3. REINFORCE / policy gradient: treat routing as an RL problem
     - Router is the policy, loss reduction is the reward
     - High variance, needs baselines
  4. No gradient to router at all: router trained only via aux load-balancing loss
     - Simplest, but router can't learn content-dependent specialization from main loss
- Q: does the choice of router training strategy affect layer specialization patterns?

** Key experimental questions
1. Does the router learn to specialize layers for different content types?
2. Can fewer routing steps + specialized layers match more steps with generic layers? (or same number of compute steps, routed, beat out a fixed transformer?)
3. Does the router use different layers for different data distributions (e.g., prose vs XML in enwik8)?
4. Does removing the load-balancing loss cause layer collapse?

* Experiment 1: enwik8 three-way comparison
** Models (compute-matched)
- Baseline GPT: 8 distinct layers, each applied once
- Looped Transformer: 1 shared layer, looped 8 times (+ timestep embeddings)
- ChoosyTransformer: 8 layers in pool, 8 routing steps

** Metrics
*** All models
- BPC on test set (overall)
- BPC stratified by content type (XML tags, prose, numbers, whitespace, entities)
- Gradient/parameter norms per layer
- Layer contribution: per-layer residual delta norm (how much each block changes the hidden state)
  - In the baseline, layers specialize /passively/ by their position in the stack
  - In the choosy model, layers specialize /actively/ by content
  - Comparing these two tells us whether routing adds meaningful specialization
    beyond what positional ordering already provides
  - For the looped transformer, this shows whether the shared block does
    qualitatively different work at different iterations (via the timestep embedding)

*** ChoosyTransformer-specific
- Layer utilization heatmap (content_type × layer_id): which layers fire for which content
- Routing entropy: is the router confident or uncertain in its selections?

** Content type analysis
enwik8 is Wikipedia XML, naturally containing distinct byte-level content types:
- XML markup: <tag>, </tag>, attributes
- Prose: English text (article bodies)
- Numbers: digits, dates, statistics
- Whitespace: structural formatting
- Markup entities: &amp;, &lt;, &#NNN;

Hypothesis: the ChoosyTransformer should route different content types to different layers.
If it does, we have evidence of learned specialization.

- Routing entropy = 0.0 across all choosy runs

- Seed 271 is an outlier (3.19 BPC) → routing instability across inits
- Content-type BPC pattern (xml < entity < whitespace < prose < number) identical across all models

* Experiment 1.1: fix routing collapse
** Motivation
Exp1 showed the Gumbel-softmax ST router collapses to always selecting one layer.
The router finds a local optimum early and never explores — no gradient signal from
unselected layers saying "I could have done better."

** Approach: temperature annealing + balancing loss sweep
- All runs use temperature annealing: 2.0 → 0.5 over training
  - High temp early → Gumbel noise dominates → near-uniform layer selection → all layers train
  - Low temp late → router logits dominate → sharp specialized routing
- Sweep balancing loss weight: 0.01, 0.005, 0.05, 0.1, 0.25, 0.5, 1.0
  - 0.01 is the control (same as exp1 but with annealing)
  - Want to find the sweet spot: enough to prevent collapse, not so much it hurts BPC

** Key questions
1. Does annealing alone (weight=0.01) fix the collapse?
2. What balancing weight gives best BPC while maintaining layer diversity?
3. Is there a tradeoff: higher balance → more layer diversity but worse BPC?
4. Does the routing pattern differ by content type at any weight?

** Results (exp1.1, 3 seeds, toy config, all with annealing 2.0→0.5)
| Balance wt | BPC (s42) | BPC (s137) | BPC (s271) | Mean |
|------------+-----------+------------+------------+------|
|      0.005 |      2.88 |       2.80 |       2.90 | 2.86 |
|       0.01 |      2.89 |       2.84 |       2.97 | 2.90 |
|       0.05 |      2.88 |       2.67 |       2.84 | 2.80 |
|        0.1 |      2.80 |       2.81 |       2.76 | 2.79 |
|       0.25 |      2.75 |       2.76 |       2.69 | 2.73 |
|        0.5 |      3.00 |       3.02 |       2.79 | 2.94 |
|        1.0 |      2.63 |       2.66 |       2.76 | 2.68 |
(reference: Regular=2.65, Looped=2.72)

*** FINDING: annealing alone doesn't fix collapse
- Low weights (0.005, 0.01) still collapse — annealing is necessary but not sufficient
- Weight 1.0 gets best BPC (2.68, matching regular) but routing is *uniform*
- Weight 0.25 is most consistent across seeds (low variance)
- Weight 0.5 is a consistent dip — unstable middle ground

*** FINDING: routing trajectory analysis
- bal1.0: ONE fixed trajectory for all inputs [0,3,2,1] — it's a regular transformer in disguise
- bal0.25: 2 trajectories, XML gets a different path from prose (at seq_len=64)
- bal0.1: 4 trajectories, content-dependent with layer reuse (prose repeats L1, XML repeats L3)
- But the content-dependent routing (bal0.1) gives WORSE BPC than uniform (bal1.0)
- The router's specialization isn't paying off — uniform parameter utilization wins

*** FINDING: architectural limitation identified
- Router uses sequence-level mean-pooling → one decision per step for entire sequence
- At seq_len=256, sequences are mixed content — the router can't see fine-grained content types
- At seq_len=64 (eval only), purer sequences reveal content-dependent routing exists
- But the model was trained at seq_len=256, so the routing was never incentivized to specialize
- The router is also stateless across steps — no memory of what layers were already applied

* Experiment 1.2: scaled-up GRU router
** Motivation
Exp1.1 showed the router's two main limitations:
1. Mean-pool erases content specificity (sequence-level decision for mixed content)
2. No memory across steps (stateless: doesn't know what's been applied)

Addressing (2) first: replace stateless mean-pool with a recurrent content vector (GRU)
that accumulates routing context across steps. Also scale up to full-size models and
sweep learning rate + schedule to find better training dynamics.

** Architecture changes
- GRU content vector: at each step, summary = mean_pool(x), content = GRU(summary, content_prev)
- Router input: content + step_embedding (vs old: mean_pool(x) + step_embedding)
- Step embeddings (sinusoidal, as in looped transformer) — already added in exp1.1 code
- Stacked parameter pool replaces lax.switch — O(1) JIT regardless of pool size
  (full 8×8 model: JIT went from 7+ min to 59s)

** Setup
- Full scale: d_model=512, 8 heads, d_ff=2048, 15K steps
- Balance weights: {0.01, 0.1, 0.25, 1.0}
- Learning rates: {3e-4, 6e-4, 1e-3}
- Schedules: {constant, cosine w/ 500-step warmup}
- Annealing: 2.0 → 0.5 (all choosy runs)
- Seeds: {42, 137}
- Plus baselines (Regular-8L, Looped-8x) at same LR/schedule grid

** Key questions
1. Does the GRU give the router enough context to meaningfully specialize layers?
2. Does scale (28M params vs 1.2M) change the routing collapse dynamics?
3. Does cosine+warmup help the router explore before committing?
4. Can choosy match or beat the baselines with genuine routing, not just uniform utilization?

*** FINDING: GRU content vector did not change routing behavior
- Best BPC runs (bal0.25) still show perfectly uniform routing (0.125 per layer)
- No content-type differentiation: prose and XML get identical layer distributions
- The one run with non-uniform routing (bal0.1-lr1e-3-cos: layer 2 at 22%, layer 3 at 4%)
  shows slight XML/prose differences but worse BPC
- Same pattern as exp1.1: uniform routing = best BPC, smart routing = worse BPC

*** FINDING: choosy converges to emulating a regular transformer
- At every scale and configuration tested, the best choosy model is one that routes uniformly
- Uniform routing with distinct blocks = regular transformer with permuted layer ordering
- The router never learns to do something a fixed ordering can't
- Choosy beats looped (1.52 vs 1.63) but only because it has 5× more params (distinct vs shared blocks)
- Choosy never beats regular (same param count), and is 0.02 BPC behind at best

*** Experiment 1 series: overall conclusions
Three experiments (exp1, exp1.1, exp1.2) spanning:
- 2 scales: toy (d=128, 1.2M params) and full (d=512, 28M params)
- 7 balance loss weights, 3 learning rates, 2 LR schedules
- Temperature annealing (2.0 → 0.5)
- GRU content vector for routing context
- Step embeddings for routing step awareness
- 3 architectures: Regular, Looped, Choosy

Consistent finding: *sequence-level routing from a layer pool does not beat a fixed
sequential transformer on byte-level language modeling (enwik8).* The router either
collapses (always picks one layer) or is forced into uniform distribution (emulating
a fixed transformer). Content-dependent specialization exists at low balance weights
but hurts BPC rather than helping it.

The hypothesis "learned dynamic routing can outperform fixed layer ordering" is NOT
supported for this architecture + dataset combination. Possible reasons:
1. Sequence-level mean-pool routing is too coarse (content signal washed out)
2. enwik8 is too homogeneous (77% prose, limited content diversity)
3. The routing overhead + gradient signal issues outweigh any specialization benefit
4. A fixed ordering may already be near-optimal for autoregressive byte-level LM

Directions for experiment 2:
- Adaptive depth (learn when to stop) instead of layer selection
- Per-segment routing (finer granularity without full per-token routing)
- Multi-domain dataset where content genuinely differs
- Investigate if the idea works better as an inference-time optimization
  (skip layers for easy inputs) rather than a training-time architecture

* Related work
** Universal Transformers (Dehghani et al., 2018)
- https://arxiv.org/abs/1807.03819
- Original looped transformer: single block, shared weights, applied T times
- Adds sinusoidal timestep embeddings so model knows which iteration
- Optional ACT (Adaptive Computation Time) for per-position halting
- Key result: Turing-complete with input-dependent depth

** Looped Transformers as Programmable Computers (Giannou et al., 2023)
- https://arxiv.org/abs/2301.13196
- Theoretical: 13-layer looped TF can simulate a general-purpose computer

** LoopFormer (Jeddi et al., 2026)
- https://arxiv.org/abs/2602.11451
- Shortcut-consistency training for elastic depth
- Different from our work: same shared weights repeated, no routing/choice

** Mixture-of-Depths (Raposo et al., 2024)
- https://arxiv.org/abs/2404.02258
- Per-token routing to skip layers (top-k routing)
- Different axis: their tokens skip layers, our model chooses layers
